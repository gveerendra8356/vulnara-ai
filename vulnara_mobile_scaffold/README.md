# Vulnara Mobile (Task 6)

Flutter companion app: scan trigger + authorization confirmation, live
scan status over the WebSocket, push notifications on `alert.critical`,
a simplified threat summary, and a lightweight remediation approve/reject
screen.

**Important — this project was NOT built/compiled.** The sandbox that
generated this code has no Flutter SDK and no network access to pub.dev,
so unlike the Python backend (which was venv-installed, byte-compiled,
and import-tested for real), this Dart code is careful hand-written and
hand-reviewed, not compiler-verified. Two real bugs were caught this way
during writing and fixed (see "Known issues fixed while writing this" at
the bottom) but `flutter analyze` may still surface more. Run it as your
very first step.

## What's here

Only `lib/`, `pubspec.yaml`, and this README -- **not** a full Flutter
project (no `android/`, `ios/`, `.gitignore`, etc.), because those are
normally generated by `flutter create` and would just be stale
boilerplate coming from a machine without the Flutter SDK. Step 1 below
generates them for real, then this `lib/` overlays on top.

## Setup — run these in order

### 1. Scaffold a real Flutter project and drop this code in

```bash
flutter create -t app --org com.vulnara --project-name vulnara_mobile vulnara_mobile_scaffold
cd vulnara_mobile_scaffold
rm -rf lib test
cp -r /path/to/this/vulnara_mobile/lib .
cp -r /path/to/this/vulnara_mobile/test .
cp /path/to/this/vulnara_mobile/pubspec.yaml .
flutter pub get
```

### 2. Point it at your backend

Edit `lib/core/constants.dart`:
```dart
static const String baseUrl = 'https://your-actual-backend-host';
static const String wsBaseUrl = 'wss://your-actual-backend-host';
```
Use `http://10.0.2.2:8000` / `ws://10.0.2.2:8000` for `baseUrl`/`wsBaseUrl`
if you're running the backend locally and testing on the Android
emulator (10.0.2.2 is the emulator's alias for your host machine's
localhost).

### 3. Firebase / FCM setup

1. Create a Firebase project at https://console.firebase.google.com if
   you don't have one.
2. Add an Android app (package name must match `--org` above, e.g.
   `com.vulnara.vulnara_mobile`) and/or an iOS app. Download
   `google-services.json` (Android) / `GoogleService-Info.plist` (iOS)
   when prompted and place them where the Firebase console tells you to
   (`android/app/` and `ios/Runner/` respectively).
3. Install the FlutterFire CLI once: `dart pub global activate flutterfire_cli`
4. From the project root: `flutterfire configure` -- select your
   Firebase project, select Android/iOS. This **overwrites**
   `lib/firebase_options.dart` with real values; the copy in this
   handoff is a deliberate non-functional placeholder, delete it first.
5. Android only: `android/app/build.gradle` needs
   `minSdkVersion 21` or higher (FCM requirement) -- `flutter create`'s
   default is already high enough on recent Flutter versions, but check.
6. Also add these permissions if `flutter create` didn't already
   (recent templates usually have INTERNET by default):
   ```xml
   <uses-permission android:name="android.permission.INTERNET" />
   <uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
   ```
   in `android/app/src/main/AndroidManifest.xml`.

### 4. Backend side (already done, see handoff notes)

The backend now has `POST /devices/register` and sends a push via
Firebase Admin whenever `alert.critical` fires. For that to actually
send anything (not just no-op), set on the backend:
```bash
export FIREBASE_CREDENTIALS_PATH=/path/to/serviceAccountKey.json
```
Generate that service-account JSON from Firebase console -> Project
Settings -> Service Accounts -> Generate new private key. This is a
*different* file from `google-services.json`/`GoogleService-Info.plist`
-- those are for the client apps, this one is for the backend's Admin
SDK. Without this env var set, the backend just logs a warning and
skips push silently (scans still work fine, WebSocket alerts still
work, you just get no push notification).

Also run the new migration against your Neon database:
```bash
psql "$DATABASE_URL" -f vulnara-backend/migrations/003_add_device_tokens.sql
```

### 5. Run it

```bash
flutter analyze          # do this first -- see the warning above
flutter run
```

## Build order this was written in (per your request)

1. **Core infra** -- models, `api_client.dart` (JWT attach + refresh),
   `secure_storage.dart`. Everything else depends on this.
2. **Auth** -- `auth_repository.dart`, `auth_provider.dart`,
   `login_screen.dart`. Nothing else is reachable without a session.
3. **Scan creation + list** -- `new_scan_screen.dart` (the
   authorization-confirmation gate), `scan_list_screen.dart` (home).
4. **Live WebSocket status** -- `websocket_service.dart`,
   `scan_status_provider.dart`, `scan_status_screen.dart`. The
   differentiator feature; needs an existing scan to test against.
5. **Push notifications** -- `push_notification_service.dart`,
   `device_repository.dart`, `POST /devices/register` on the backend.
   Depends on auth existing (registers a token right after login) and
   ties into the scan-status feature (`alert.critical`).
6. **Remediation approve/reject** -- `remediation_list_screen.dart`,
   `remediation_approval_screen.dart`. Last, since it needs a
   remediation to already exist (generated via the web dashboard, per
   Task 4/5's `POST /vulnerabilities/{vuln_id}/remediations`).

## Known API-contract subtlety this code relies on

`GET /scans/{scan_id}/remediations` (contract 5.3) is labeled
"Client: Web" in the contract doc, but the contract's own conventions
section says that label just documents expected usage, not a technical
restriction -- "both clients hit the identical API." Mobile's
remediation-list screen calls this endpoint deliberately (filtered to
`status=PENDING`) since there's no other way to discover which
remediations are awaiting a decision for a given scan. Flagging this
explicitly so it doesn't look like an oversight.

## New backend surface added in this task (not in the original contract)

- `POST /devices/register` -- register an FCM token for the logged-in
  user. Needed because nothing in the Task 1 schema or Task 2 contract
  anticipated push notifications.
- `DeviceTokens` table (migration 003).

## Known issues fixed while writing this

- **Refresh token bug**: first draft of `api_client.dart` assumed
  `POST /auth/refresh` rotates the refresh token and tried to read a
  new one out of the response. Contract 1.3 only returns
  `{ access_token, expires_in }` -- no new refresh token. Would have
  thrown a null-cast error on every single token refresh. Fixed to keep
  reusing the existing refresh token.
- **const constructor bug**: `SeverityCounts.zero` was declared
  `static const` but the class had a non-const constructor -- that's a
  compile error in Dart, not a runtime one, so `flutter analyze` would
  have caught it immediately, but fixed proactively since I can't run
  that check here.
- A throwaway platform-detection helper for FCM registration
  (`defaultTargetPlatformIsIOS()`) was written as a meaningless stub in
  a first pass and replaced with the real `defaultTargetPlatform` check
  from `package:flutter/foundation.dart`.

## Fixed after a real `flutter analyze` run (thank you for running it)

The first handoff was analyzer-clean by hand-review only; you then ran
`flutter analyze` for real and it caught what hand-review couldn't:

- **31 "dangling library doc comment" infos** -- every file's top
  `///`-style file-description comment wasn't attached to a `library;`
  directive, which Dart's newer linter flags. Fixed by converting those
  to plain `//` comments (they were documentation for a human reader
  anyway, not doc-comment API surface, so this loses nothing).
- **2 "deprecated_member_use" infos** -- `Color.withOpacity()` is
  deprecated in favor of `Color.withValues(alpha:)` on your SDK version.
  Fixed both call sites.
- **1 real error**: `test/widget_test.dart` (the default file
  `flutter create` generates, not something I originally delivered)
  referenced `MyApp`, a class that doesn't exist -- our root widget is
  `VulnaraApp`. This package now includes a corrected `test/widget_test.dart`
  that imports the real class; copy it into your scaffold's `test/`
  folder the same way you copied `lib/`.
  **One caveat on that replacement test, flagged rather than assumed
  away**: `AuthNotifier` calls `flutter_secure_storage` (a
  platform-channel plugin) immediately on construction. Plain widget
  tests don't have platform channels wired up by default, so this test
  may throw `MissingPluginException` instead of cleanly reaching the
  login screen -- I have no Flutter toolchain here to confirm either
  way. If it fails that way, mock the channel per
  flutter_secure_storage's testing docs, or override
  `secureStorageProvider` in the test's `ProviderScope`.
