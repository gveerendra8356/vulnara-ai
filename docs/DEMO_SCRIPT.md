## 3. Run a live scan (2 min) — *the core*

**Do:** **Scans → New Scan**. Target: `pentest-ground.com:6379`. Fill the authorization justification, tick authorize, turn **Active AI Testing ON**, submit.
**Say:** "Every scan is gated behind an explicit authorization check — enforced server-side. That's the ethical-scanning design; we only scan hosts we're permitted to."

**Do:** Watch the status change PENDING → IN PROGRESS → COMPLETED **without refreshing**.
**Say:** "Status updates stream live over WebSockets. Behind the scenes the scanner does recon — host discovery and a TCP-connect port scan run concurrently with async I/O, plus banner grabbing to identify services."

## 4. AI analysis + the ML model (2 min) — *the differentiators*

**Do:** Open the completed scan, click a finding (e.g. the Redis CVE-2016-8339).
**Say, pointing at each panel:**
- "**Severity and CVSS** come from the CVE database — CVSS is the industry-standard 0–10 score."
- "**AI reasoning** — this text is generated by a large language model. The pipeline is Retrieval-Augmented Generation: we retrieve candidate CVEs from the NVD database, feed them to the model with the scan context, and it reasons about whether each applies, with a **confidence score**. Notice it says 'version not disclosed, so confidence is low' — it reasons about *uncertainty* instead of hallucinating, which reduces false positives."
- "**ML Priority** — this is a *separate, trained machine-learning model* I built. It's a Logistic Regression classifier that predicts exploit-likelihood from scan context — CVSS, whether active testing verified it, service risk, unauthenticated exposure, AI confidence. It complements CVSS: a high-CVSS finding with no exploit context can score a *lower* priority than an active-verified one."

**Say (key line):** "So there are two kinds of intelligence: a pre-trained LLM used via RAG for explanation, and my own trained classifier for prioritisation — evaluated at F1 0.81, ROC-AUC 0.91 (see the evaluation report)."

## Algorithm & AI cheat-sheet (memorise this)

| Part | Technique / algorithm |
|---|---|
| Port scan | TCP connect scan, concurrent async I/O (nmap when available) |
| Service ID | Banner grabbing (HTTP headers / raw TCP) |
| CVE matching | Keyword retrieval from NVD (not ML) |
| AI triage & remediation | Pre-trained **LLM** (`gpt-oss-120b` via Groq) in a **RAG** pipeline; Transformer architecture (self-attention, autoregressive generation); structured JSON output + retry loop |
| Active testing | Differential response analysis + LLM verification |
| **ML prioritisation** | **Logistic Regression** (trained, 9 features, evaluated F1 0.81 / ROC-AUC 0.91); pure-numpy inference in production |
| Severity | CVSS v3 (industry standard) |
| Auth | JWT (HMAC-SHA256), bcrypt password hashing, single-use reset tokens |
| Access control | Server-side RBAC + `department_id` filtering |
| Real-time | WebSockets |

## Likely questions & answers

- **"Did you train the AI yourself?"** — "Two parts. The *explanation* AI is a pre-trained LLM used via Retrieval-Augmented Generation — training a security LLM needs massive data and compute, which is out of scope. But I *did* train my own ML model — a Logistic Regression classifier for prioritisation — with a full pipeline: data generation, model comparison against Decision Tree and Random Forest, cross-validation, and evaluation."
- **"Why Logistic Regression and not deep learning?"** — "It won on F1, it's interpretable — I can show exactly which features drive priority — and it deploys with zero heavy dependencies. Over-engineering with a neural net on tabular data with nine features wouldn't help."
- **"Where's the training data from?"** — "Synthetic, generated from a documented domain-driven labelling function with noise, because labelled real-world exploitation data is proprietary and scarce — the public EPSS project motivates the same idea. The generator is in the repo and fully reproducible."
- **"How do you avoid false positives?"** — "Three layers: CVE retrieval gives candidates, the LLM filters them with a confidence score, and active testing verifies exploitability by differential response analysis."
- **"Is it secure?"** — "JWT sessions (HS256), bcrypt password hashing, single-use reset tokens, server-side RBAC and department scoping, and an authorization gate on every scan."
- **"How does it scale / what are the limits?"** — "It does active scanning of authorized hosts, not passive wire-level traffic monitoring — that needs network sensors, a different class of system. The scheduler is in-process, fine for a single backend; a multi-worker deployment would move to Celery/APScheduler. These are documented trade-offs."

## If something breaks live (recovery)

- **"Network Error" on a scan** → the Render backend was asleep; wait ~30–50s and retry (first request wakes it).
- **A scan fails** → the target may be unreachable from the cloud; switch to `scanme.nmap.org` or `pentest-ground.com:6379`, which respond reliably.
- Have one **pre-run completed scan** ready to open, so you can show findings even if a live scan is slow.
